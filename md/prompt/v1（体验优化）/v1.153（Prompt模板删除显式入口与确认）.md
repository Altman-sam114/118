- 版本号：`v1.153`
- 任务名：Prompt 模板删除显式入口与确认
- 阶段：`v1（体验优化）`
- 基线版本：`v1.152`

- 提交主题：`v1.153: Prompt delete confirmation`
- 版本依据：人工已确认 v1.152 通过 Agent C 验收。本轮在不改变 Prompt Library 数据模型和既有业务能力的前提下，为当前只能通过 swipe 立即删除的模板补充可发现的显式入口，并把所有删除入口统一收口到带模板名的确认流程，因此按同一体验优化阶段递增为 v1.153。

## 背景与现状问题

`LocalDiffusion/Views/Prompts/PromptLibraryView.swift` 当前在每个 `PromptTemplateRow` 中只显示 Edit 和 Load 两个操作。模板删除仅由分组 `ForEach` 后的 `.onDelete` 提供，并在 swipe 后立即执行 `modelContext.delete` 和 `save()`。

这造成两个问题：

1. iPad 指针、全键盘访问和 VoiceOver 用户难以发现删除能力，因为删除没有稳定的行内控件。
2. swipe 会立即删除，没有展示目标模板名的确认步骤，容易误删。

本轮必须把显式 Delete 与现有 swipe 统一接到同一份待删除状态和同一个确认对话框。删除仍是 Prompt Library UI 对 SwiftData `PromptTemplate` 的既有操作，不新增跨层服务或数据模型。

## 目标

1. 在每个 Prompt 模板行增加明确的 Delete 按钮，使用系统 `trash` 图标、既有危险色和既有 Sci-Fi 次级按钮样式。
2. Delete 必须是原生 SwiftUI `Button`，具有至少 44 x 44pt 命中区、系统 pointer hover affordance、模板名上下文的 VoiceOver label/value/hint，并可由 Full Keyboard Access 聚焦和触发。
3. 行内 Delete 与现有 swipe 删除必须调用同一个 `requestDeleteTemplate(_:)` 请求入口；两个入口均不得直接删除。
4. 增加标题可见的 confirmation dialog，明确显示待删除模板名，并提供 destructive Confirm 与 cancel Cancel。
5. Cancel、对话框手势关闭或系统取消只清空待删除状态，不删除任何模板。
6. Confirm 只按待删除状态记录的稳定模板 ID 删除唯一目标，保存 SwiftData 后清空状态；不得根据当前搜索位置、分类 offset 或变化后的数组位置删除。
7. 保持 SwiftData schema、PromptTemplate 字段、Edit/Load、搜索、分类、添加、编辑、加载和生成参数业务边界不变。
8. 三个行内操作在窄宽度和 Dynamic Type 下不得溢出、遮挡或压缩到小于 44pt。
9. 同步 README、核心流程、流程图和更新日志，使文档反映新的统一确认流程。

## 非目标

- 不增加批量删除、撤销、回收站、归档、恢复、toast、删除队列或第二次确认。
- 不改变模板创建、保存、编辑、加载、排序、搜索匹配、分类重命名或分类清除行为。
- 不改变模板行 metric pills、prompt 摘要、颜色主题或面板结构，除容纳第三个操作所必需的局部布局外不做视觉重构。
- 不修改 `PromptTemplate` SwiftData schema、迁移、唯一约束或持久化位置。
- 不修改 `GenerationViewModel`、`AppFileStore`、模型下载、Gallery、Plan、StoreKit、native backend、bridge、Xcode project 或 workflow。
- 不新增全局键盘快捷键；每行重复注册 Delete 快捷键会产生目标歧义。
- 不新增测试 target、第三方依赖、分支或 PR 流程。
- 默认不在本机运行 xcodebuild、simulator、真实 VoiceOver 或真实 GGUF 生成。

## 架构依据

- `PromptLibraryView` 位于 `LocalDiffusion/Views/Prompts/**` UI 层，当前已通过 `@Query` 和 `modelContext` 管理 `PromptTemplate`；本轮继续留在该边界内。
- `PromptTemplateRow` 只负责显示和发出 Edit/Load/Delete 用户意图，不应直接持有 `ModelContext` 或执行数据删除。
- 删除请求和确认状态由 `PromptLibraryView` 持有，确认后才调用 `modelContext.delete`，与仓库内 Models/Gallery 的 pending deletion + confirmation dialog 模式一致。
- 删除目标必须由 `PromptTemplate.id` 识别。确认时从当前 `templates` 查询结果按 ID 找到目标，避免搜索、分类变化或列表 offset 变化导致误删。
- UI 仍不接触 `ImageGenerationBackend` 或 C/Objective-C++ bridge，推理边界完全不变。

## 具体实现步骤

### 1. 建立单目标待删除状态

在 `PromptLibraryView.swift` 内增加局部私有状态类型，例如 `PromptTemplateDeletionState`，至少保存：

- `templateID: UUID`
- `templateName: String`
- 可供 SwiftUI 使用的稳定 `id`

在 `PromptLibraryView` 增加 `@State private var pendingTemplateDeletion: PromptTemplateDeletionState?`。不得只保存列表 offset；不得用模板名作为删除主键。

### 2. 统一删除请求入口

新增 `requestDeleteTemplate(_ template: PromptTemplate)`，其唯一职责是使用模板的 ID 和当时名称建立待删除状态。

- `PromptTemplateRow` 新增 `onDelete` closure，行内 Delete 只调用该 closure。
- 分组列表的 `.onDelete` 从 `group.templates` 解析当前 swipe 的单一模板后，也只调用 `requestDeleteTemplate(_:)`。
- 删除 `.onDelete` 中现有的立即 `modelContext.delete` / `save()`。
- 当前页面没有批量编辑入口；若收到非单一 offsets，不得无确认批量删除或循环覆盖 pending target。应只接受可明确确认的单一目标，否则不执行删除。

### 3. 只在确认后删除唯一目标

新增 `performPendingTemplateDeletion()`：

1. guard 读取 pending state。
2. 用 `templateID` 在当前 `templates` 中查找完全相同的模板。
3. 只对该对象执行一次 `modelContext.delete`。
4. 沿用当前 `try? modelContext.save()` 行为，不在本轮扩展错误处理架构。
5. 无论目标已不存在还是正常完成，都清空 pending state；目标不存在时不得改删其他模板。

不得在确认时重新使用 section index、搜索结果 index、模板名匹配或 `offsets.first` 推导目标。

### 4. 增加带模板名的确认对话框

在 `PromptLibraryView` 根视图现有 sheet/dialog 修饰符区域增加统一 confirmation dialog：

- 标题使用 `Delete template?` 并设置 `titleVisibility: .visible`。
- message 必须包含当前 `templateName`，并明确模板会从 Prompt Library 删除且不可撤销。
- destructive 按钮可见文案使用 `Delete Template`，只调用 `performPendingTemplateDeletion()`。
- cancel 按钮可见文案使用 `Cancel`，只清空 pending state。
- 使用自定义 `Binding<Bool>` 连接 optional pending state；系统关闭对话框时必须清空状态且不删除。
- 为 Confirm 和 Cancel 都提供包含模板名的 accessibility label、value 和 hint。Confirm hint 明确永久删除该保存模板；Cancel hint 明确保留模板并关闭确认。

### 5. 增加显式行内 Delete

在 `PromptTemplateRow` 的操作顺序中保留 Edit、Load，并在其后增加 Delete：

- `Label("Delete Template", systemImage: "trash")`
- 横向紧凑布局可继续 `.labelStyle(.iconOnly)`，但必须保留完整语义 label。
- 使用 `SciFiSecondaryButtonStyle(color: SciFiTheme.danger)` 和至少 44 x 44pt frame。
- accessibility label 必须包含模板名，例如 `Delete Template: <name>`。
- accessibility value 使用模板名；hint 明确会先显示确认，而不是立即删除。
- 可增加 `.help("Delete Template")` 提供指针停留说明；不得用 `onTapGesture`、隐藏 context menu 或仅 swipe 代替原生按钮。
- 更新模板行整体 accessibility hint，使其准确列出 Edit、Load 和 Delete controls，并说明删除需要确认。

### 6. 窄宽度与 Dynamic Type 布局

三个操作不可继续假设始终能在一个 `HStack` 中容纳：

- 普通 Dynamic Type 且宽度足够时，保持 Edit -> Load -> Delete 横排，三个按钮均保持稳定 44pt 最小尺寸。
- 普通 Dynamic Type 的窄宽度路径必须通过 SwiftUI 原生响应式布局回退，优先 `ViewThatFits(in: .horizontal)`，横排 action group 不 fit 时改为纵向 action group；不得硬编码设备型号或屏幕宽度。
- 横排候选需按三个控件的真实固有宽度参与 fit 判断，避免把按钮压缩后误判为可容纳；可对横排 action group 使用适当的 horizontal fixed size。
- accessibility Dynamic Type 直接使用纵向 actions，不先尝试三个按钮横排。
- 模板行既有普通字号 header 横排优先/纵排回退继续成立；可拆分 `horizontalActions` 和 `stackedActions` 私有局部 View，避免外层 header 与内层 actions 的嵌套 fit 产生溢出。
- 纵向回退保持 leading 对齐、稳定间距和每项 44pt 命中区；不得让操作覆盖模板文本或 metric pills。
- 保持模板名和 prompt 的既有 Dynamic Type 行数策略，除修复实际溢出所必需外不修改 metric pills。

## iPad 指针、键盘与 VoiceOver 设计

- iPad pointer：trash 图标作为稳定可见入口，沿用 `SciFiSecondaryButtonStyle` 的系统 hover effect；`.help` 提供 Delete Template 文本提示。
- 键盘：使用原生 `Button` 保证 Full Keyboard Access 可聚焦和激活，焦点顺序为 Edit、Load、Delete；不注册会在多行间产生歧义的全局 Delete shortcut。
- VoiceOver：模板行保持 `.accessibilityElement(children: .contain)`，Delete 作为独立子控件可被遍历；label/value/hint 均带模板名上下文，确认对话框的 Confirm/Cancel 也带同一模板名。
- 读取顺序：模板摘要在前，Edit、Load、Delete 依次出现；删除请求后由系统 confirmation dialog 接管焦点语义。
- 不能只靠红色表达 destructive；必须同时使用 trash 图标、Delete 语义、destructive role 和明确确认文案。
- accessibility Dynamic Type 下操作纵排，避免三个 44pt 按钮横向挤压；可见文本和辅助功能文本不得与相邻内容重叠或截断。

## 必须保持不变的行为

- Edit 仍只打开当前模板编辑器，保存逻辑不变。
- Load 仍只把当前模板加载到 Generate 并执行既有 `onLoad()` 导航回调。
- 搜索仍匹配 name/category/positive prompt/negative prompt。
- 分类分组、排序、重命名、清除到 Uncategorized 和分类清除确认流程不变。
- Add/New Template 和 Generate Save Template 行为不变。
- PromptTemplate schema、参数字段、SwiftData container 和 generation 数据流不变。
- 只有用户确认的目标模板被删除；Cancel、dismiss 和找不到原目标均删除零个模板。

## 风险

- 若 swipe 仍保留直接删除代码，两个入口会产生不一致并继续存在误删风险。
- 若 pending state 只保存 offset 或按名称查找，搜索、分类变化或重名模板可能删除错误目标。
- 若 optional dialog binding 在系统 dismiss 时不清空，旧目标可能污染下一次确认。
- 第三个 44pt 操作会增加行内最小宽度；若横排候选可被压缩或 accessibility 仍横排，会出现溢出和重叠。
- 图标按钮若缺少模板名 label/hint，VoiceOver 和键盘焦点用户仍难以判断目标与后果。
- 云端 build 不能替代真实 pointer、Full Keyboard Access、VoiceOver 和窄 Split View 目检；未人工执行时必须保留该风险。
