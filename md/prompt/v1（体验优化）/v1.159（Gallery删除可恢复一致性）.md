- v1.64 已为 Gallery 详情 Reuse / Regenerate / Share / Delete 保留当前图片的 VoiceOver 上下文；v1.94 已为 Delete confirmation 的确认/取消按钮补齐图片上下文和文件/metadata 语义；v1.156 已确立局部失败恢复、明确错误、禁止全局 `ModelContext.rollback()` 的边界。本轮在不破坏这些既有语义的前提下，修复 Gallery 图片删除的文件与 SwiftData 一致性。

## 背景

当前 `GalleryView.deleteImage(_:)` 的顺序是：

1. `try? fileStore.removeImageFile(...)` 永久删除 PNG；
2. 在 Gallery 共用的主 `modelContext` 上 `delete(image)`；
3. 无条件清理 `focusedImageID` 和 `detailPath`；
4. `try? modelContext.save()` 静默吞掉 metadata 保存错误。

`ImageDetailView` 的 destructive confirmation 又会在 `onDelete()` 后无条件 `dismiss()`。因此只要 metadata save 失败，就可能出现 PNG 已永久消失、SwiftData 记录仍在、详情已退出且用户没有任何错误反馈的状态；主 context 还可能保留失败删除产生的未保存状态。

本轮必须把删除设计成局部、明确、可恢复的状态机：先把 PNG 原子式移动到同卷暂存位置，再使用独立短生命周期 `ModelContext` 按图片 UUID fetch/delete/save；metadata 失败时恢复 PNG；metadata 成功后才 finalize 暂存文件。任何部分失败都必须返回真实结果，不得继续沿用 `try?` 或把逻辑删除、残留暂存文件伪称为“两边都成功”。

## 目标

- 在 `AppFileStore` 内提供 Gallery PNG 删除暂存 token，至少包含唯一 UUID、原始 URL、暂存 URL，并能明确表示原文件在 stage 开始时是否已缺失。
- 暂存目录必须位于 `imagesURL` 所在文件系统/卷内；stage 使用 move，不使用 `/tmp`、跨卷 copy 或先永久 remove。
- 为 stage、restore、finalize 提供最小、明确、可重试/可判定幂等的 API；失败不得覆盖同名文件或吞掉底层错误。
- Gallery 删除 metadata 时新建独立短生命周期 `ModelContext(modelContext.container)`，只按 `GeneratedImage.id` fetch 目标，delete 后显式 `save()`；不得把主 context 中的 `GeneratedImage` 实例传入该 context 删除。
- metadata fetch/delete/save 失败时，丢弃该短生命周期 context，并优先恢复已 stage 的 PNG；不得污染或 rollback Gallery 主 context。
- metadata 已不存在视为幂等的 metadata 终态，不重新插入伪 metadata；若 PNG 已 stage，则继续 finalize。
- metadata 成功删除后 finalize 暂存 PNG；finalize 失败必须返回“Gallery metadata 已逻辑删除、暂存 PNG 清理待完成”的部分失败，保留 token 和暂存文件，并提供当前会话内 Retry Cleanup，不得声称文件和 metadata 均已删除。
- restore 失败必须保留 token 和暂存文件，并提供 Retry Restore；在恢复完成前不得重新开始 metadata 删除或误报成功。
- 原 PNG 已缺失时不得制造空文件或伪造 stage 成功：继续尝试删除 metadata 以收敛为两边都不存在；若 metadata 删除失败，明确说明 PNG 本来已缺失且 metadata 仍保留，并允许重试 metadata 删除。
- ImageDetail 删除确认只有完整成功才调用 `dismiss()`；失败时保留可操作、可访问反馈。父级 `detailPath` / `focusedImageID` 只能在完整成功时主动更新。
- 对重复确认、重复 callback、重复 Retry Restore / Retry Cleanup 做守卫或幂等处理，避免同一 request 被并发执行、重复删除或 token 串线。
- 保留 v1.64/v1.94 的图片上下文 VoiceOver 语义，并让删除中、恢复失败、cleanup pending 和重试操作的 visible/VoiceOver 文案与真实状态一致。

## 当前架构依据

### Gallery 删除入口

- `LocalDiffusion/Views/Gallery/GalleryView.swift` 的 `ImageDetailView` 负责确认、反馈和 dismiss；外层 `GalleryView` 负责 query、navigation path 和删除编排。
- 当前详情按 `GeneratedImage.id` 注册 `navigationDestination(for: UUID.self)`，`detailPath` 也是 UUID 数组；稳定 UUID 应是删除 request 和独立 context fetch 的唯一身份。
- `@Query` 可能在独立 context save 后移除当前 `GeneratedImage`，所以 finalize/restore 错误不能只存放在可能随 query 刷新消失的 `ImageDetailView`。至少需要让父级 `GalleryView` 持有 request/state/error/token，并把确认结果或禁用状态传给详情。
- v1.64/v1.94 的 toolbar 与 confirmation VoiceOver label/value/hint 必须保留；可更新 hint 使其准确描述“确认后安全删除”，但不能丢失当前图片 model/seed/size 上下文。

### SwiftData 边界

- App 通过一个 `ModelContainer` 注入 SwiftUI 环境；现有 `modelContext` 可访问其 `container`。
- 每次删除使用新的短生命周期 `ModelContext(modelContext.container)`，可显式关闭 autosave，构造只匹配 UUID 的 `FetchDescriptor<GeneratedImage>`，fetch 后最多删除该唯一目标并 `save()`。
- 独立 context 只接收 UUID 等值类型，不接收主 context 管理的 `GeneratedImage` 对象；save 失败后让独立 context 生命周期结束，避免其 pending delete 留在主 UI context。
- metadata fetch 返回空数组表示对象已经不存在，是可重复调用的幂等状态，不是创建 replacement metadata 的理由。

### 本机文件系统边界

- `AppFileStore` 是 Application Support 文件 URL、目录准备和文件操作的唯一边界。
- 暂存目录建议为 `imagesURL` 下隐藏且专用的目录，例如 `.DeletionStaging`；它与 PNG 原路径同卷，并会被当前 `.skipsHiddenFiles` 的 `generatedImageFilenames()` 排除，避免本轮修改 reconciliation。
- token 应是不可变值类型，至少包含 `id: UUID`、`originalURL: URL`、`stagedURL: URL`，并包含足以区分 `.staged` 与 `.sourceMissing` 的信息。暂存文件名必须使用唯一 token id，不能覆盖已有暂存项。
- filename 必须通过本地文件边界校验：拒绝空值、路径分隔、`..`、absolute path 或标准化后逃出 `imagesURL` 的路径；stage/restore/finalize 只能操作 token 对应的 images/staging 子路径。
- stage 使用同卷 `FileManager.moveItem`。不能使用 Data 重写、copy 后先删 source、系统 Trash 或 `/private/tmp` 作为生产暂存位置。

## 删除状态机

实现可使用私有 enum/struct，命名可按现有代码风格调整，但行为必须等价于以下局部状态：

```text
idle
  -> staging(request)
  -> deletingMetadata(request, token)
  -> restoring(request, token, metadataError)
  -> finalizing(request, token, metadataDisposition)
  -> succeeded(request)

任一步失败可进入：
  stageFailed(request, error)
  metadataFailedSourceMissing(request, error)
  restorePending(request, token, metadataError, restoreError)
  cleanupPending(request, token, metadataDisposition, finalizeError)
```

约束：

- request 至少快照 `imageID`、`imageFilename` 和 v1.64/v1.94 所需的图片可访问上下文；不要在异步/重试阶段继续依赖可能已失效的 `GeneratedImage` 引用。
- 同一时刻最多一个 active request；确认按钮、Delete toolbar 和 retry action 必须由同一 state 推导 disabled/in-progress 行为。
- stale completion 必须核对 request id/token id，不能覆盖更新的请求。
- 本轮流程可以保持同步并在主 actor 上执行短文件操作/SwiftData save；若改为 async，必须显式处理 task 取消和主线程 UI 更新，但不得为此引入新并发架构。
- `succeeded` 只表示 metadata 不存在且原始/暂存 PNG 都不再存在，或原 PNG 在开始前已缺失且 metadata 已成功/已先行不存在。只有这一状态可以 dismiss 并主动清理父 navigation/focus。
- `cleanupPending` 是已提交的逻辑删除，不可逆地缺少 metadata，但仍有可恢复的暂存 PNG 残留；它不是完整成功。唯一安全重试是针对同一 token 再次 finalize，不得恢复 PNG 到 Gallery 原路径后留下 orphan，也不得伪造 metadata。
- `restorePending` 表示 metadata 仍存在、PNG 仍在暂存位置或文件位置不确定；只允许针对同一 token Retry Restore，恢复完成后回到可再次发起新删除的失败/idle 状态。

## 状态与故障矩阵

| 场景 | stage 后事实 | metadata 动作 | 文件补偿/收尾 | 最终事实 | UI、导航与可重试动作 |
| --- | --- | --- | --- | --- | --- |
| 正常删除 | 原路径无文件；暂存路径有原 PNG | 独立 context 按 UUID fetch/delete/save 成功 | finalize 删除暂存 PNG 成功 | metadata 无；原/暂存 PNG 均无 | 完整成功；清 error；父级仅此时清理匹配的 focus/path；ImageDetail 才 dismiss |
| 原 PNG 开始前已缺失 | token 明确 `.sourceMissing`，不制造暂存文件 | UUID 对象存在则 delete/save | 无 staged payload，finalize 为明确 no-op | metadata 无；PNG 原本已无 | 可作为收敛成功，文案不得声称本轮实际删除了一个存在的 PNG；成功后 dismiss |
| stage 失败且原文件仍在 | 原路径仍有 PNG；暂存无 | 不得开始 metadata 删除 | 无需 restore | 两边保持删除前状态 | 明确 stage error；不改 path/focus；详情不 dismiss；允许重新确认 |
| stage 报错但位置异常 | 必须检查/返回 token 可判定 original/staged 事实，不得假设 | 在文件归属未确定前不得删 metadata | 若 staged 存在按 restorePending 处理；冲突明确报错 | 不伪造一致性 | 保留可操作恢复反馈；禁止静默继续 |
| metadata fetch/delete/save 失败，restore 成功 | PNG 已 stage | 独立 context 失败并被丢弃；主 context 不动 | move staged PNG 回原路径成功 | metadata 保留；原 PNG 恢复；暂存无 | 明确“删除未完成，图片已恢复”；不改 path/focus；详情不 dismiss；用户可重新 Delete |
| metadata 失败，restore 失败 | PNG 仍 staged、原路径无，或显式冲突 | metadata 保留 | 不删 staged、不覆盖 original | 两边未完成一致收敛，但 PNG 仍可恢复 | `restorePending`；明确 metadata 仍在和 PNG 暂存；提供 Retry Restore；禁止重新 delete metadata |
| 原 PNG 已缺失且 metadata delete/save 失败 | 无 staged payload | 独立 context 失败并丢弃 | 无文件可恢复 | metadata 保留；PNG 缺失是既有事实 | 明确“PNG 已缺失且 metadata 未删除”；不 dismiss；允许 Retry Delete Metadata；不得说已恢复 |
| metadata 对象已不存在 | PNG 若存在则已 stage；若原本缺失则无 payload | fetch 空，视为 `.alreadyAbsent`，不 save、不 reinsert | 对 staged payload finalize | 成功时两边均无 | 幂等成功；仅 finalize 成功后更新导航/dismiss |
| metadata 成功/已不存在，但 finalize 失败 | 原路径无；暂存 PNG 保留 | metadata 已无 | 不 restore、不二次删 metadata、不删 token | Gallery 逻辑删除已提交；暂存残留待清理 | `cleanupPending`；诚实说明逻辑删除与残留；父级不主动清 path/focus；详情不主动 dismiss；提供 Retry Cleanup |
| Retry Cleanup 成功 | 暂存 PNG 被同 token finalize | 不再 fetch/delete metadata | 暂存无 | metadata 无；原/暂存均无 | 转完整成功，再按 success 规则更新 path/focus/dismiss；清旧错误 |
| Retry Cleanup 再失败 | 暂存 PNG 保留 | 不碰 metadata | 保留 token | 逻辑删除 + 残留不变 | 更新底层错误但保留 Retry Cleanup；不得报成功 |
| 重复确认/active 中再次触发 | 已有 request/token | 不启动第二 context | 不创建第二 token | 当前状态不被并发覆盖 | 按钮 disabled 或 guard no-op；不得出现双删/双 restore |
| 成功后 stale callback/重复调用 | metadata 和文件均无 | fetch 空 | missing/no-op finalize | 仍为两边无 | 幂等，不产生新错误，不操作其他图片；不能误清不同 image 的 path/focus |

额外文件 API 幂等要求：

- Restore：`staged` 存在且 `original` 不存在时 move back；`staged` 不存在且 `original` 已存在时可判定 already restored；两者都存在时禁止覆盖并报冲突；两者都不存在且 token 原本有 payload 时必须报不可恢复，不得报成功。
- Finalize：`staged` 存在时 remove；`staged` 已不存在且 `original` 也不存在时可判定 already finalized；不得把已经 restore 回原路径的文件当作 finalize 目标永久删除。
- `.sourceMissing` token 的 restore/finalize 必须是明确的 no-payload 结果，不创建文件、不删除后来出现的同名文件。

至少逐项输出 case 名与 PASS/FAIL，任一断言失败返回非零：

1. stage success：原路径消失，唯一 staged 路径存在，bytes 完全一致，token 原/暂存 URL 均位于注入 root 的 images 边界。
2. restore success：原路径恢复同样 bytes，staged 路径消失。
3. finalize success：stage 后 finalize，原路径和 staged 路径都不存在。
4. source missing：返回明确 no-payload/missing disposition，不创建 original/staged 空文件；restore/finalize 不删除之后无关路径。
5. repeated restore/finalize：already restored/already finalized 的判定符合矩阵，不误删已恢复原文件，不伪报 payload 丢失为成功。
6. unique token：同一 filename 恢复后重新 stage，token id 和 staged URL 不复用、不覆盖。
7. path boundary：空 filename、`../`、absolute/path separator 等逃逸输入被拒绝，images root 外文件不受影响。
8. staging exclusion：暂存 PNG 不出现在 `generatedImageFilenames()`。
9. stage failure：通过真实目录状态或最小注入故障确定性触发，确认 metadata 逻辑尚未被调用，原 PNG 仍可恢复且错误明确。
10. restore failure：确认 staged PNG 不被 finalize/丢弃，原文件不被覆盖，token 可用于随后 Retry Restore；解除故障后 retry 能恢复 bytes。
11. finalize failure：确认 metadata 层 outcome 可保持 logical delete、staged PNG 仍存在且 token 可重试；解除故障后 Retry Cleanup 删除 staged，原路径仍不存在。

如果 macOS 文件权限行为使某个故障无法用 chmod/目录冲突稳定触发，可使用本轮新增的最小 internal 文件操作注入点触发该系统调用错误，但成功/恢复/最终文件位置仍必须在 `/private/tmp` 的真实文件系统上断言。不得把只 grep 方法名的脚本称为真实文件 probe。

## 验收标准

- 生产删除链路不再先永久删除 PNG；AppFileStore 用 images 同卷隐藏暂存目录和唯一 token 执行 stage move。
- token 至少包含 UUID、original URL、staged URL 和 source missing/staged disposition；路径不能逃逸 images/staging 边界，暂存文件不进入 Gallery PNG 枚举。
- stage/restore/finalize 的 success、missing、already complete、conflict 和 failure 不被 `try?` 吞掉，并符合幂等规则。
- metadata 删除只使用独立短生命周期 `ModelContext(modelContext.container)` 按 UUID fetch/delete/save；主 context 不 delete、不 rollback，不接收跨 context model object。
- metadata 失败时：有 staged PNG 必须 restore；restore 成功则两边恢复删除前状态并允许新重试；restore 失败保留 token/PNG 和 Retry Restore；原 PNG 本来缺失则明确 metadata 保留且允许重试。
- metadata 对象已不存在时不 reinsert，继续安全 finalize；这是幂等 metadata 终态。
- finalize 成功才是完整成功；finalize 失败保留 staged PNG/token，明确 logical delete + cleanup pending，只重试 finalize，不伪称文件/metadata 均成功。
- ImageDetail confirmation 只在完整成功后 dismiss；失败有可操作、可访问且不会因 `@Query` 移除详情而丢失的父级反馈。
- `detailPath` 和 `focusedImageID` 只有完整成功才主动清理，且只影响匹配 UUID；失败/partial commit 不执行成功清理。
- active request、retry 和 stale callback 受 request/token identity 约束，不会并发双删、重复永久删除或串到其他图片。
- v1.64/v1.94 删除 VoiceOver 图片上下文和 v1.156 Folder/Tags 保存恢复保持有效。
- `reconcileImageFiles()`、GeneratedImage schema、生成流程、native backend、StoreKit、Xcode project、workflow 和测试规范无变化。
- 本地轻量检查、两条固定 Swift parse、真实文件状态 probe 有成功记录；SwiftData runtime probe如未运行被明确列为风险；云端 iPhoneOS build 成功。
- `origin/main` 最新 v1.159 artifact 经 Agent C 下载并核对 manifest、日志和结果后，版本才可宣布通过。

## 风险

- 文件系统 move 与 SwiftData save 无法成为真正的单一原子事务；本轮以同卷 stage + compensating restore 把可恢复窗口缩小，但进程在 stage/save/finalize 之间被强杀仍可能留下 metadata/staged file 组合。
- 本轮明确不增加跨启动 reconciliation。restorePending 或 cleanupPending 的 token 在当前 UI 会话内可重试；app 被终止后隐藏暂存文件可能保留，需作为已知残余风险记录，不能宣称具备 crash-proof transaction。
- 独立 context save 后 `@Query` 刷新时序可能让当前 detail 变为 unavailable；因此错误状态必须由父级持有。Swift parse/build 不能证明 presentation 时序，必须人工或故障注入验证。
- `ModelContext.save()` 的可控失败不易在无测试 target 环境稳定注入。若只做 source review，必须明确未实际执行 metadata save failure，不得用文件 fault probe 替代。
- Restore 时 original 路径若被其他动作重新创建，绝不能覆盖；这会进入冲突/restorePending，需要用户重试或人工处理。
- Finalize 失败后 metadata 已不存在，恢复原 PNG 会创建 orphan，且现有 reconciliation 可能删除它；所以本轮只能保留 staged payload 并重试 cleanup，不能用伪 metadata恢复 Gallery。
- 当前删除操作通常很短，但快速重复触发或多窗口/外部文件变化仍可能竞争；request/token identity 与文件状态检查必须防止误删另一张图片。
