## 背景与已证实现状

`LocalDiffusion/Views/Gallery/GalleryView.swift` 的 `ImageDetailView` 当前有两条直接 SwiftData 保存路径：

1. `folderBinding` 的 setter 先把 `image.folderID` 改为 Picker 新值，然后执行 `try? modelContext.save()`。保存失败时错误被吞掉，当前 SwiftData 对象和 Picker 仍显示新 folder，与真实持久化值不一致。
2. `saveTags()` 把 normalized `tagText` 写入 `image.tags`，执行 `try? modelContext.save()`，随后无条件把 `tagText` 回填为 `image.tags` canonical CSV。保存失败时既会把内存中的 saved-tags 基线误当成成功值，又会覆盖用户原始 `tagText` 草稿，导致 `hasUnsavedTagChanges` 错误变为 false，Save Tags 无法表达可重试状态。

相关现有边界：

- `GeneratedImage.folderID` 是图片归属的 UUID 元数据；`GeneratedImage.tags` 通过现有 setter 对 `tagString` 执行 normalization。本轮不改 schema 或 normalization。
- Folder Picker 保持选择后即时保存；Tags 保持显式 Save Tags，两者不合并、不改保存时机。
- `savedTags` 读取 `image.tags`，`draftTags` 读取 `tagText.tagsFromCSV()`，`hasUnsavedTagChanges` 为两者数组比较。失败后必须恢复这一真实比较关系，不得新建平行 dirty Bool。
- v1.154 已用 `.id(image.id)` 隔离图片草稿身份；同一图片普通重现不覆盖未保存草稿。本轮不重做身份机制。
- 项目已有 SwiftUI `.alert` + 明确取消按钮的局部错误反馈惯例。本轮可使用同类原生反馈，但 Folder 和 Tags 必须共用同一份 `ImageDetailView` 局部、可识别错误状态。

## 目标

1. Folder Picker 选择后仍立即尝试保存；保存成功时保留新 `folderID`，行为与现有产品语义一致。
2. Folder 保存失败时，只把 `image.folderID` 恢复为该次尝试前的旧 folder ID（包括 `nil`），使 Picker、VoiceOver value 和当前内存模型重新反映旧持久化值。
3. Save Tags 成功时保留 v1.154 行为：写入 normalized tags，然后以实际 `image.tags` 回填 canonical CSV，`hasUnsavedTagChanges` 恢复 false，Save Tags 禁用。
4. Save Tags 失败时，把 `image.tags` 恢复为保存尝试前的旧已持久化 tags，但完整保留用户当时的 `tagText` 草稿，不做 canonical 回填。
5. Tags 失败后 `savedTags` 必须重新反映旧值，`draftTags` 仍反映用户草稿，因而原本可保存的变更继续满足 `hasUnsavedTagChanges == true`，Save Tags 保持启用并可直接重试。
6. Folder 和 Tags 失败共用同一份局部、可识别错误状态，根据 operation 提供不混淆的 alert/confirmation 或项目一致可访问错误反馈。
7. 错误反馈必须明确说明失败的操作、已恢复/保留的状态以及用户如何重试，并对 VoiceOver 提供明确 label/value/hint 或原生等价语义。
8. 每次 Folder 或 Tags 新保存开始时清理过期错误；成功时也确保过期错误为 nil，不得在后续操作中重现旧失败。
9. 两条目标保存路径都必须使用显式 `do` / `try` / `catch`，不得继续用 `try? modelContext.save()` 吞错。
10. 保持 Gallery 现有暗色科幻风格、Form 布局、44pt 按钮、Dynamic Type、Picker/TextField 原生交互和详情删除确认不变。

## 当前架构依据

- `ImageDetailView` 位于 `LocalDiffusion/Views/Gallery/**` UI 层，已持有 `ModelContext`、Picker binding、tag 草稿和本地 confirmation state。本轮的赋值、尝试保存、失败恢复和用户反馈可留在这一局部边界。
- `GeneratedImage` 是 SwiftData reference model。赋值后 `save()` 失败不会自动使 UI 回到已持久值，因此必须在赋值前捕获该属性旧值，并在 `catch` 中只恢复该次修改的属性。
- Folder 与 Tags 可共用一个请求级 error state，但两者的业务恢复不得混合：Folder 恢复 old `folderID`；Tags 恢复 old `image.tags` 并保留 old `tagText` draft。
- `hasUnsavedTagChanges` 继续是 Save Tags 启用、VoiceOver state 和可重试性的唯一 dirty-state 真相源；不得为失败另建 `isDirty` 并手工切换。
- 不能调用 `modelContext.rollback()`。`ModelContext` 可能还跟踪同一 context 中其他未保存更改，全上下文 rollback 会越界破坏无关状态。
- UI 继续不直接调用 C/Objective-C++ bridge，不接触文件存储或生成后端。

## 详细实现步骤

### 1. 建立唯一局部可识别错误状态

在 `ImageDetailView` 内或 `GalleryView.swift` 同文件私有范围定义最小错误类型，例如 operation 为 folder/tags 的 `Identifiable` value，并由唯一个 optional `@State` 持有。具体命名可按现有风格调整，但必须满足：

- 同一状态同时区分 Folder 与 Tags，不建两个平行 alert Bool/string。
- 状态可识别，使每次失败都能作为新事件展示，不因相同文案被 SwiftUI 误当旧状态。
- 错误消息可包含 `error.localizedDescription`，但必须有稳定的用户向操作上下文，不能只显示原始技术错误。
- 任一 Folder/Tags 新保存开始立即设为 nil；成功后保持 nil；只在 `catch` 中设置对应新错误。
- 切换到另一图片 ID 时不得把上一图片错误带入新详情；现有 `.id(image.id)` 应自然提供局部身份边界，只需核对，不建跨图片错误缓存。

### 2. Folder Picker 保存实现原子化 UI 恢复

把 `folderBinding` setter 的静默保存收敛到局部方法或等价清晰结构，顺序必须为：

1. 在任何赋值前捕获 `previousFolderID = image.folderID`。
2. 可对新旧值相同做无副作用 early return；不得为相同值制造伪保存或错误。
3. 新保存真正开始时清理过期详情保存错误。
4. 把 `image.folderID` 设为 Picker 新值，使成功路径仍保持即时选择。
5. 使用 `do { try modelContext.save() } catch { ... }`。
6. 成功时保留新值且错误状态为 nil。
7. 失败时先且只将 `image.folderID = previousFolderID`，然后设置 Folder operation 错误。不调用第二次 `save()`，不用 `try?`，不删除对象，不重建 context。

Folder 错误反馈至少要告诉用户：文件夹选择未能保存，已恢复之前的文件夹，可关闭后重新选择以重试。Picker 的 `currentFolderAccessibilityValue` 必须因恢复后的 `image.folderID` 而自然回到旧值。

### 3. Save Tags 保存保留草稿与真实 saved state

重写 `saveTags()` 的目标路径，顺序必须为：

1. 保留现有 Save Tags `.disabled(!hasUnsavedTagChanges)`，并在 action 中用同一 dirty state 做最小 guard，防止非按钮调用路径在无变更时保存。
2. 在修改 model 前捕获 `previousTags = image.tags` 和用户当时完整的 `draftText = tagText`。
3. 只解析一次 normalized 草稿，沿用 `tagText.tagsFromCSV()` 和 `GeneratedImage.tags` setter，不复制 normalization。
4. 新保存开始时清理过期错误，再把 normalized tags 赋给 `image.tags`。
5. 使用 `do { try modelContext.save() } catch { ... }`。
6. 成功时才执行 `tagText = image.tags.joined(separator: ", ")`，保留 v1.154 canonical 回填，并由现有比较自然得到 `hasUnsavedTagChanges == false`。
7. 失败时先且只恢复 `image.tags = previousTags`，并确保 `tagText` 仍为原始 `draftText`。不得进入 canonical 回填，不得清空、trim 或其他方式改写用户原文草稿。
8. 设置 Tags operation 错误，说明已保留草稿，用户可关闭错误后再次使用 Save Tags。

失败后必须由真实数据自然满足：

```text
image.tags == previousTags
tagText == draftText
draftTags != savedTags
hasUnsavedTagChanges == true
Save Tags enabled
```

不得通过强制 `isDirty = true`、额外存一份 saved-tags 快照并长期代替 `image.tags`，或修改 `.disabled` 逻辑来制造上述结果。

### 4. 提供明确且可访问的错误反馈

首选使用项目已有的原生 SwiftUI alert 模式，例如基于可识别错误 item 的 `.alert`；若采用项目一致的等价 confirmation/error feedback，也必须达到以下语义：

- Folder 和 Tags 显示不同、明确的失败标题或 operation value。
- Folder message 说明已恢复之前 folder，要重试请再次选择。
- Tags message 说明已恢复已保存 tags 且保留草稿，要重试请再次按 Save Tags。
- 提供明确的 `OK` / `Dismiss` / 等价取消操作，关闭只清理错误 state，不改 folder、tags 或草稿。
- 原生 alert 标题、message 和 button 要能被 VoiceOver 按操作顺序读取；如果自定义按钮语义，补充明确 accessibility label/value/hint，不只依赖颜色、icon 或技术错误文本。
- 错误反馈不得嵌套 card、遮挡 Organization 表单或改变删除 confirmation 的语义。

### 5. 保持局部性与可测性

- 预期生产源码 diff 仅限 `GalleryView.swift` 中 `ImageDetailView` 及同文件最小 private 辅助类型。不得重构整个 Gallery。
- 现有仓库没有测试 target。不要为本轮新建大型测试架构或改 Xcode project。
- 若为了对成功/失败转移做可执行测试，可抽取一个文件内最小 helper、纯状态转移函数，或只包含 `save()` 的窄 protocol/closure 故障注入点。它只能服务本轮 Folder/Tags 路径，不得变成 repository/service/ViewModel 或扩展到其他页面。
- 不得为测试改变生产行为；无法实际注入 `ModelContext.save()` 失败时，必须明确把失败交互矩阵记为静态审查/待人工故障注入，不得伪造已运行结果。

### 保存成功/失败行为矩阵

Agent B 必须对以下各项区分“实际运行”、“可控 save 故障注入”、“静态源码审查”和“待人工 UI 验证”，不得混用或伪造：

- Folder 从 A 选到 B，save 成功：`image.folderID == B`，Picker/VoiceOver 显示 B，无过期错误。
- Folder 从 A 选到 B，save 失败：`image.folderID == A`，Picker/VoiceOver 恢复 A，错误说明恢复与重试。
- Folder 从 None 选到 folder 失败、从 folder 选 None 失败：均精确恢复之前 optional UUID。
- Folder 选择相同值：不应制造多余 save、错误或 UI 闪动。
- Tags 有变更，save 成功：`image.tags` 为 normalized 值，`tagText` 为 canonical CSV，dirty false，Save 禁用。
- Tags 有变更，save 失败：`image.tags` 为失败前旧值，`tagText` 与用户点击时字符级草稿一致，dirty true，Save 仍启用，错误说明草稿保留与重试。
- Tags 清空保存失败：旧 tags 恢复，空草稿保留，因为 normalized 草稿与 saved 旧值不同，Save 仍启用。
- Tags 包含大小写、多余空格、重复或无效 token，保存失败：完整原文 `tagText` 保留，不做 canonical 回填。
- 失败 alert 关闭：只清 error state，不改已恢复 folder、saved tags 或 tag 草稿。
- Folder 失败后发起 Tags 新保存，或 Tags 失败后发起 Folder 新保存：新开始立即清除前一过期错误，成功后不重现。
- 图片 A 失败或有未保存草稿后切换图片 B：B 使用自己的 folder/tags，不显示 A 的草稿或错误。
- VoiceOver 能获得失败 operation、恢复/草稿保留结果、关闭操作与重试方式；反馈不只靠颜色或 icon。
- 现有 Delete Image confirmation 与新保存错误反馈不重叠、不误触发。
- iPhone/iPad、普通/accessibility Dynamic Type 下 Organization 表单不截断、不重叠，Picker/TextField/Save Tags 原有交互不变。

本轮默认不要求 Agent B 在本机运行完整 `xcodebuild`、simulator smoke、真实 VoiceOver、Full Keyboard Access、iPad Split View 或真机 GGUF。原因是改动局限于 Gallery 详情的 SwiftData 属性恢复与错误 UI，本地以 Swift parse 覆盖语法，完整 iPhoneOS build 交给 push 后 GitHub Actions。但是 Swift parse 和云端 build 不能证明 save 失败转移或 VoiceOver 交互正确；未执行的故障注入、交互和视觉项必须记为残余风险。

## 验收标准

- `ImageDetailView` 的 Folder Picker 和 Save Tags 两条目标路径使用显式 `do` / `try` / `catch`，不再使用 `try? modelContext.save()`。
- Folder 成功时仍为即时保存；失败时 `image.folderID`、Picker 和 VoiceOver value 恢复为保存前旧 optional UUID。
- Tags 成功时仍写入 normalized tags、canonical 回填 `tagText`、dirty false 并禁用 Save Tags。
- Tags 失败时 `image.tags` 恢复为保存前旧值，`tagText` 保留用户点击时完整草稿，不做 canonical 回填，`hasUnsavedTagChanges` 继续 true 且 Save Tags 可重试。
- Folder 与 Tags 共用同一局部可识别错误 state；反馈明确区分 operation，说明恢复/草稿保留结果和重试操作，并对 VoiceOver 可理解。
- 每次新 Folder/Tags 保存开始和保存成功都清理过期错误；失败之间不串 operation，切换图片不泄漏错误。
- 失败恢复只赋回当次目标属性，没有 `modelContext.rollback()`、没有第二次静默 save，不影响同一 context 中其他状态。
- v1.154 的 normalized dirty-state gate、成功 canonical 回填、图片 ID 草稿边界和 tag filter saved-only 语义全部保留。
- New/Rename Folder、v1.155 validation、SwiftData schema、filter/sort、file storage、native backend、StoreKit、Xcode project、workflow 和测试规范无变化。
- README、flow、flowchart、update log 已按实际代码更新，未运行的故障注入、VoiceOver、iPad、Dynamic Type 等项被如实记录。
- Agent B 本地轻量检查和两条固定 Swift parse 退出 0；`origin/main` 最新 v1.156 run 的未加密 artifact 经 Agent C 下载、核对并通过。

## 风险

- `ModelContext.save()` 保存的是 context 中的变更集，错误未必由当次 folder/tags 字段单独引起。本轮只能精确恢复当次 UI 修改，不得通过全 context rollback “清理”其他状态。
- 把旧值捕获放在赋值之后会导致失败恢复新值，形成伪恢复；Agent C 必须审查语句顺序。
- Tags `catch` 后若继续执行成功路径的 canonical 回填，会再次丢失用户草稿；成功/失败分支必须结构清晰。
- SwiftUI Picker binding setter 中同步 `save()` 失败后立即恢复可能产生短暂视觉更新；验收重点是最终可见/VoiceOver 状态与旧持久值一致，不得为消除短暂更新改成非即时保存产品流。
- 原生 alert 与现有 Delete confirmation 都挂在详情 View，必须避免同时竞争或错误 dismiss 改动删除 state。
- 云端 build 不能覆盖真实 SwiftData save 失败、VoiceOver 操作顺序和 iPad/Dynamic Type 视觉验收。若没有故障注入或实际 UI 验证，必须保留明确风险。

## 禁止项

- 禁止在 Folder Picker 和 Save Tags 目标保存路径继续使用 `try? modelContext.save()`，禁止空 `catch`、只 log 不恢复或伪造成功。
- 禁止使用 `modelContext.rollback()`、重建/replace ModelContext、重新 fetch 整个 Gallery 或删除/reinsert `GeneratedImage` 来恢复单字段。
