## 背景

当前 `RootContentView` 以唯一 `@State private var selection: AppSection = .generate` 作为全局主导航真相源：compact `TabView(selection:)`、regular `NavigationSplitView` 的 sidebar binding，以及 Gallery/Models/Generate/Prompts 的跨页回调都读写该状态。现有五个入口依次为 Generate、Models、Gallery、Prompts、Plan，但尚无可发现的硬件键盘主导航命令。

`LocalDiffusionApp` 的正常启动分支创建 `RootContentView`；SwiftData container 创建失败时只显示 `StartupFailureView`，此时不存在有效 Root selection。命令必须在正常 Root 场景写回现有 selection，并在启动失败场景保持禁用，不能创建第二份 selection 或全局状态来掩盖该边界。

本机 Xcode 26.6 / iPhoneOS SDK 26.5 的公开 SwiftUI swiftinterface 已核对：

- `Commands`、`CommandMenu`、`FocusedBinding` 和 View `keyboardShortcut` 从 iOS 14 起可用。
- key-path 版本的 `focusedSceneValue` 从 iOS 15 起可用。
- `CommandMenu + @FocusedBinding + .focusedSceneValue + Command-数字` 最小代码已用 `swiftc -typecheck -target arm64-apple-ios17.0` 验证可编译。
- 项目部署下限为 iOS/iPadOS 17，因此该公开 API 架构满足可用性要求。
- 工程仍为 iPhone/iPad target，`SUPPORTED_PLATFORMS = "iphoneos iphonesimulator"`、`SUPPORTS_MACCATALYST = NO`；本轮不能声称、暗示或验收 Mac/Catalyst 支持。

## 目标

- 为 iPad 硬件键盘提供以下主导航快捷键：
  - Command-1：Generate
  - Command-2：Models
  - Command-3：Gallery
  - Command-4：Prompts
  - Command-5：Plan
- 使用 Scene `Commands` 和 `FocusedValue` / `FocusedBinding` 的公开 SwiftUI 架构，把命令写回 `RootContentView` 现有 `$selection`。
- compact `TabView` 与 regular `NavigationSplitView` 继续由同一个 selection 同步；尺寸类别切换后不产生状态分叉。
- 提供命名清楚、系统可发现的菜单命令；菜单与每个 action 的可见名称必须明确表达导航目标。
- `StartupFailureView` 没有有效 selection binding 时，五条命令全部 disabled，触发快捷键不得产生导航或隐藏状态。
- 可按需要让 `AppSection` 提供稳定顺序、标题和快捷键元数据，并复用这些元数据减少 tab/sidebar/commands 的重复声明；不得重复创建页面实例或 navigation selection。

## 非目标

- 不修改 Generate、Models、Gallery、Prompts、Plan 页面业务、数据流或用户操作。
- 不修改任何页面内部 `NavigationStack`、Gallery detail path、focused image handoff 或既有跨页回调语义。
- 不启用 Mac Catalyst，不增加 macOS target、Mac 菜单特例、Mac 构建设置或桌面发行能力，不声称 Mac 支持。
- 不修改 SwiftData schema、文件存储、下载状态、生成 ViewModel、native backend/bridge、StoreKit、Plan entitlement 或 CI workflow。
- 不增加全局单例、通知中心导航、环境对象导航 store、第二份 selection、命令专用 selection 或页面级快捷键状态。
- 不做视觉重设计，不新增屏幕内快捷键说明、隐藏控件或调试 UI。

## 架构与 API 依据

1. `RootContentView.selection` 保持唯一主导航真相源。`TabView(selection:)`、sidebar optional binding、`sectionContent(selection)` 和已有回调继续共享它。
2. 在 SwiftUI focused values 中定义一个窄的 selection binding key，例如值类型为 `Binding<AppSection>`；正常 Root 用 `.focusedSceneValue` 暴露现有 `$selection`。
3. 在独立、最小的 `Commands` 类型中用 `@FocusedBinding` 读取该 binding。Command action 只赋值目标 `AppSection`，不持有 `@State`、对象或 fallback selection。
4. 在 `LocalDiffusionApp` 的 `WindowGroup` scene 上通过 `.commands` 注册一个清楚命名的 `CommandMenu`，例如 `Navigate`；每条 Button 使用明确名称，例如 `Show Generate`，并注册对应 `.keyboardShortcut("1"..."5", modifiers: .command)`。
5. 每条命令的 disabled 状态直接来自 focused binding 是否存在。正常 Root 有 binding；`StartupFailureView` 不注入伪 binding，因此命令自然禁用。
6. 使用 `focusedSceneValue` 而不是依赖某个 TextField/row 当前焦点的局部 `focusedValue`，确保用户在正常场景任一页面编辑内容时，命令仍指向该 scene 的现有 Root selection。
7. `AppSection` 可改为 `CaseIterable` 或提供等价的唯一 ordered metadata。Generate...Plan 的顺序和 Command-1...5 映射必须集中定义并由 tab、sidebar、commands 复用；如果为 SwiftUI `KeyEquivalent` 做最小转换，应从同一数字元数据派生。
8. 不要求为消除少量 switch 而抽取大型导航框架。`sectionContent(_:)` 仍是唯一页面构造入口，不能在 command 定义中实例化页面。

## 风险

- `.focusedValue` 若只挂在当前有键盘焦点的子视图，TextField/弹层焦点变化可能使命令失效；本轮应使用 scene 范围的 focused value 并做人工输入焦点测试。
- 给 commands 另设默认 `.generate` binding 会使 StartupFailureView 看似可导航，掩盖无 Root selection 的真实状态，必须禁止。
- tab/sidebar/commands 若分别维护数组，后续新增 section 容易产生顺序和快捷键漂移；应集中元数据并由 mapping probe 守护。
- Swift parse 只能检查语法，mapping probe 只能检查映射，云端 build 只能证明编译集成；系统菜单发现性、硬件键盘事件、焦点与尺寸类别切换仍需 iPad 交互验证。
- 当前工程没有 Mac Catalyst target；iPad Commands API 可用不等于 Mac 支持或 Mac 菜单已验收。
